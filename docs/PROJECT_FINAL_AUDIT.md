# MyAI 项目总体审计与最终 Checkpoint

审计日期：2026-08-17

审计对象：MyAI 0.11.0-local 源码、文档、实验档案、测试/质量门禁与 Windows 便携 App Demo

结论等级：**毕业设计核心范围完成；本地单机产品化基线完成；生产级发布仍有明确边界。**

## 1. 总体结论

与最初发现的主要工程缺陷和后续四阶段路线相比，项目已经完成绝大部分约定工作：

- Stage 1 的安全、隔离与可复现基线已经完成；
- Stage 2 的真实本地开源模型、冻结实验条件、记忆/RAG 对比和多维指标已经完成，并形成可校验的正式证据；
- Stage 3 的统一生命周期、依赖注入、持久化运行关系、异步记忆维护和统一韧性模型已经完成，达到单 Python runtime MVP 的验收范围；
- Stage 4 已按最终选择收敛为“可交付的本地个人智能体 App Demo”，完成跨电脑 Windows 便携包、前端模块化和本地/CI 同构质量门禁。完整标准 MCP 客户端、容器化、原生安装器和公网部署属于未来扩展，不再作为此 Demo checkpoint 的未完成验收项。

因此，MyAI 已从“功能较多但缺少可信基线的毕业设计原型”推进为“有真实模型证据、运行治理、测试门禁和可迁移交付物的本地个人智能体”。它尚不是多用户、云原生、商业生产级产品，不能把这一边界模糊为“全部完成”。

## 2. 与原项目题名的契合度

项目题名“**MyAI：基于开源大模型的个人智能助手设计与实现**”与当前实现高度一致。

| 题名要素 | 对应实现 | 审计判断 |
| --- | --- | --- |
| 基于开源大模型 | OpenAI-compatible provider 接入本地 Ollama；Qwen2.5 1.5B 负责生成，BGE-M3 负责 embedding；正式实验记录版本、摘要和 CPU-only 运行状态 | 符合。模型权重不随仓库分发，需用户本地安装 |
| 个人 | 用户/会话归属、长期记忆作用域、个人知识库、本地数据边界、只读工具权限 | 符合单机个人使用定位 |
| 智能助手 | 对话、记忆、RAG、引用、任务规划、工具执行、健康探测、运行轨迹 | 符合，且超出单纯聊天机器人 |
| 设计与实现 | Java/Python 分层架构、统一运行时、持久化模型、异常治理、对比实验、测试和便携交付 | 符合，可说明设计取舍与工程验证 |

需要避免两种过度表述：

1. “基于开源大模型”不代表仓库本身已经选择并附带开源许可证；
2. Stub 模式证明功能链路和可安装性，不证明真实模型质量，真实能力应引用 Stage 2 和最新健康探测。

## 3. 原始缺陷与修复闭环

| 原始工程缺陷 | 对应阶段 | 当前结果 | 剩余边界 |
| --- | --- | --- | --- |
| 服务默认边界和工具权限不够保守 | Stage 1 | Java/Python 回环绑定、文件系统工具默认关闭、敏感路径拒绝、任务归属校验 | Python 服务间调用仍无独立认证，不支持公网暴露 |
| Stub 回退可能掩盖真实模型不可用 | Stage 1/2 | 回退可配置、严格实验关闭回退、真实 embedding 失败即关闭、模型健康探测 | 日常模式仍允许显式 Stub 回退 |
| 测试共享 Chroma/知识库/记忆配置 | Stage 1 | 测试使用隔离临时存储，仓库门禁阻止运行产物进入 Git | 长时间真实数据迁移仍需单独演练 |
| 缺少通用本地模型 provider | Stage 2 | 已实现 OpenAI-compatible provider，并验证 Ollama | 不随包内置运行时和模型 |
| 缺少固定模型、数据、硬件与统计口径 | Stage 2 | 固定 spec、数据集、摘要、随机种子、模型信息、资源采样与校验和 | 样本为小型合成集，外部有效性有限 |
| 没有记忆/RAG 对比实验 | Stage 2 | none/basic/governed 与 vector/hybrid/hybrid_rerank 两组消融完成 | 当前 RAG 数据在 Top-3 召回上饱和 |
| 模块由导入期单例分散拥有 | Stage 3 | AppRuntime 由 FastAPI lifespan 创建并通过依赖注入共享 | 仅支持单应用 worker |
| AgentRun/TaskRun 缺少持久关系 | Stage 3 | Python SQLite 持久化运行、步骤、事件和幂等记录，建立完整逻辑链 | 无跨 Java/Python 外键和级联删除 |
| 记忆维护位于聊天热路径 | Stage 3 | 合并/衰减进入有界、合并请求的后台维护池，前台采用非阻塞准入 | 队列和跳过的前台工作不持久 |
| 超时、重试与错误结构分散 | Stage 3 | 统一协作式 deadline、熔断、退避、幂等、安全错误和关联标识 | 无法硬终止已阻塞线程，副作用工具不保证 exactly-once |
| 跨电脑运行困难 | Stage 4 | allowlist 构建、完整文件清单、外部 ZIP 校验和、setup/doctor/start/stop/status/reset | 目标机仍需 Python 3.12 与 Java 17+ |
| 前端单文件过大 | Stage 4 | 保留 Thymeleaf 契约，拆分外部 CSS 与七个职责脚本 | 尚非组件化前端或 SPA |
| 缺少持续质量门禁 | Stage 4 | 本地 PowerShell 门禁与 Windows GitHub Actions 工作流已定义 | 远端通过状态必须以具体 GitHub 提交为准 |

## 4. 核心证据审计

### 4.1 Stage 2 正式实验

- 证据目录：**reports/experiments/thesis-core-v1-r2-final/**
- 数据规模：18 个记忆唯一案例、30 个 RAG 唯一案例、每个方案 3 次技术重复；
- 总尝试：432/432 成功，记录的模型/基础设施失败率为 0%；
- 记忆结论：治理记忆总体规则准确率 61.11%，基础记忆 50.00%，无记忆 33.33%；治理收益主要来自安全拒答；
- RAG 结论：三种方案 Support Hit@3 均为 100%，纯向量总体规则准确率反而最高；证据不支持“混合或重排必然更优”；
- 完整性：正式目录固定八个文件，提供 SHA-256，指标、原始输出和引用均经过独立复核。

这些证据足以支撑毕业设计中的“方案对比、工程可复现性、性能和资源分析”，但不足以支撑普适性学术结论或生产可靠性声明。

正式实验 manifest 与 CHECKSUMS 保留运行当时的源码 commit SHA 和证据摘要。
后续审计发现旧本机配置凭据曾进入仅用于开发的提交历史，因此 GitHub
公开 checkpoint 必须使用净化历史，不能直接发布该本地工作分支。净化后
源码在功能上等价，但新 commit SHA 与正式运行记录的 SHA 不同；本次没有
在冻结 Ollama 0.32.6 环境重跑 432 次实验，因此不得把新 SHA 宣称为正式
实验的原始代码身份，也不得篡改 manifest/CHECKSUMS 伪造对应关系。

### 4.2 Stage 3 运行时

- Memory、Knowledge、Task、Agent 由一个 lifespan-owned AppRuntime 统一拥有；
- user → conversation → agent_run → task_run 关系可持久检查；
- 重启时将中断运行标记为失败，不自动重放未知副作用；
- 记忆整理与聊天解耦，使用有界并发、请求合并和非阻塞锁准入；
- 任务/聊天共享 deadline、熔断、有限退避、幂等和安全错误结构。

结论：第三阶段在“单 Python 运行时 MVP”定义下完整结束；分布式队列、跨进程租约、硬取消、加密和跨服务删除属于生产强化，不是未完成的当前验收项。

### 4.3 Stage 4 交付

- Windows 便携 ZIP 只打包 allowlist 内容，不包含本地 .env、数据库、日志、模型、上传文档、Chroma 和虚拟环境；
- manifest 记录包内每个文件的长度与 SHA-256，ZIP 具有相邻外部校验和；
- 可在含空格的新路径完成 setup、doctor、start、status、stop 和 reset；
- 可变数据位于包内 data/runtime/config 边界，停止和重置具备进程/路径所有权检查；
- README 已加入合成账户截图，不包含真实对话或本机绝对路径。

结论：第四阶段选择的“可交付本地 App Demo”范围完成。标准 MCP 互操作、MSI/MSIX、签名、内置运行时/模型、容器化和公网部署可作为毕业设计后的产品路线。

## 5. 工程管理审计

### 已建立

- 根级 VERSION 和发布说明；
- 分阶段 plan、execution log、closeout、known limitations 与 release checklist；
- Python 依赖精确固定；
- Java 与 Python 自动化测试；
- Markdown 链接、敏感配置、运行产物、前端脚本等静态门禁；
- GitHub Actions Windows 工作流定义；
- 便携包 allowlist、清单、校验和和安全控制测试；
- .gitignore/.gitattributes 对环境文件、数据库、日志、模型和实验证据行尾的治理。

### 仍需补齐

按优先级排序：

1. **公开发布门禁**：推送前检查待发布提交的完整可达历史，不得把仅在本机修复过的敏感内容随旧提交带到远端；只发布审计后的干净分支。
2. **远端 CI 证据**：首次推送后观察 GitHub Actions，并把通过的提交链接或截图写入发布记录；当前文档不声称远端已通过。
3. **许可证决策**：仓库尚无 LICENSE。公开可读不等于允许复制、修改或分发；维护者应在 MIT、Apache-2.0 或保留全部权利之间明确选择。
4. **发布管理**：建立 GitHub Release、语义版本 tag、变更日志与可下载 ZIP/校验和；后续可增加 SBOM、签名和 provenance。
5. **协作治理**：启用分支保护、必需检查、CODEOWNERS、Issue/PR 模板和 Dependabot/Renovate。
6. **数据生命周期**：实现统一导出、保留期限、跨 Java/Python 删除和 SQLite/日志敏感数据治理。
7. **生产韧性**：只有在决定走部署产品路线时，再增加服务认证、加密、耐久队列、多进程协调、可观测导出与容器/安装器。

## 7. GitHub 发布 Checkpoint

公开分支在推送前必须满足：

- 工作树只包含明确审计过的代码、文档和合成截图；
- .env、密码、token、私钥、数据库、日志、模型、向量库和真实上传文档均未被跟踪；
- 静态质量门禁、完整 Python/Java 回归和差异格式检查通过；
- 待推送分支的可达历史通过敏感信息复核；
- 发布分支由受审计源码生成净化历史，不包含旧本机配置凭据事件所在的
  开发提交；
- README 的启动命令在干净环境中可执行；
- 首次净化发布说明真实模型、单 worker、回环边界、许可证待定和远端 CI 状态。

由于远端 `main` 的初始历史本身包含已轮换前的本机开发凭据，首次操作必须先完成凭据轮换和受控历史替换；普通 feature branch 或 Pull Request 不能清除 `main` 的旧可达对象。待净化 `main`、远端 CI 和安全设置验证完成后，后续变更再恢复 feature branch + Draft Pull Request 流程，并启用分支保护。

Stage 2 证据的来源身份与公开发布身份必须分别表达：正式报告继续引用其
原始 commit SHA；公开 checkpoint 引用净化后的新 SHA，并说明“功能等价，
未在冻结环境重新执行正式实验”。如未来需要严格复现实验与公开源码 SHA
一致，再按已冻结协议完整重跑并生成一套新的、不覆盖历史记录的证据目录。

## 8. 展示与后续路线

当前截图足以让访问者快速理解界面。为了面试与答辩，建议维护者另行录制 60–90 秒演示视频，使用全新合成账户和合成知识文档，展示：

1. Ollama 四角色健康探测；
2. 一轮带执行轨迹的对话；
3. 上传合成文档并返回引用；
4. 记忆待确认/历史治理；
5. 任务时间线；
6. 便携包 doctor 与启动。

视频上传到 GitHub Release、个人作品集或公开视频平台后，可在 README 增加链接。不要把真实账户、桌面目录、访问令牌、本地日志或个人对话录入素材。

后续建议按价值排序：

1. 轮换旧开发凭据、净化远端 `main` 并完成首次远端 CI；
2. 恢复 Draft PR/分支保护流程，并确定许可证、Release 与演示视频；
3. 扩充真实用户/公开数据集，增加更强模型和检索基线；
4. 改善引用生成与检索拒答门；
5. 根据目标岗位选择标准 MCP 客户端、原生安装器或容器化其中一条，不同时铺开；
6. 若转向生产系统，再推进认证、加密、耐久队列、多实例和数据删除闭环。
